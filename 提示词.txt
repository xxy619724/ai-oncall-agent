1什么是提示词工程（Prompt Engineering）
官方标准定义：不改动大模型内部参数，通过设计、组织、测试、迭代优化输入文本，让大模型输出更稳定、可控、贴合任务要求。
通俗理解：
不是提升大模型本身底层推理智商，而是给模型划定清晰输入输出约束、规定思考流程，把模型现有能力充分释放。
3 核心易混概念区分
预训练 Pre-Training：从 0 初始化全部神经元参数，完整从零训练一套全新大模型，成本极高；
微调 Fine-Tuning：在已训练完成的开源模型基础上，少量更新部分参数，适配垂直细分领域（医疗、代码等），能真正提升模型领域智能；
提示词工程：只改输入文本，全程不动模型参数，无法提升模型底层推理能力。
二、大模型底层基础原理
1 大模型本质结构
底层载体：海量安全张量（safe tensors）切片文件，几十 GB~ 上百 GB，存储亿万浮点型神经元权重参数；
运行依赖：GPU 分布式集群加载切片文件，构建神经网络实例；
底层计算：模型只识别数值，人类文字、图片、音频必须转为向量（Embedding 词元）才能送入网络计算。
2 Token 分词流程
Token（词元）：文本最小切割单位，中文单字 / 词语、英文单词 / 子词；
流程：自然语言→分词切割为 Token→向量化 Embedding→送入神经网络层层概率计算；
生成逻辑：大模型是概率生成模型，每一步基于前文预测下一个词的概率分布，无绝对标准答案，因此相同提示词多次输出会有细微差异。
三、优质提示词工程师必备四大核心能力
1）结构化语言表达能力
不用华丽散文，要求清晰、量化、分层，规避模糊口语（尽量详细、大概等无量化描述禁用）；
2）任务拆解与架构思维
将复杂大需求拆分为多段子任务（如高并发服务、聊天客户端分步拆解），是软件工程底层思维；
3）量化测试 & 验收思维
给输出制定明确验收标准，提供测试用例验证结果（如写完算法附带多组测试用例）；
4）安全、隐私、成本三重意识
（1）安全意识
业务权限安全：禁止提示词跨库、越权访问企业内部数据；
提示注入防护：抵御黑客通过诱导提示绕过安全校验、泄露服务器 IP；
内容安全：政治、宗教、生物病毒、伦理类内容强制拦截，规避合规风险。
（2）隐私意识
禁止在提示词明文传入 API 密钥、账号密码、用户敏感信息，防止数据留存泄露；
（3）Token 成本意识
提示词精简、分层，冗余描述会大幅增加输入 Token，提升调用计费成本。
四、写prompt-书写Markdown 语法
业务需求：清晰定义整体目标、使用场景、使用人群；
任务拆解：分步列出模型执行步骤，逐条清晰；
成功验收标准：量化输出合格条件、格式、范围、禁止内容；
错误兜底逻辑：输出不达标时的二次处理规则（重新生成 / 报错提示）。
输入框快捷键：Windows Ctrl+Enter 换行；

五、提示词工程落地场景（企业项目真实应用）
场景 1：意图识别（智能客服核心）
任务：用户输入文本，判定有限枚举意图（退款 / 物流 / 账户咨询 / 其他）；
Prompt 设计：设定分类身份、限定输出仅标签、兜底「其他」，无多余解释；
业务链路：意图识别结果分流至不同知识库 / 数据库查询流程。

场景 2：合同 / 文档字段抽取（RAG 配套）
任务：从长合同文本提取指定结构化信息（甲方、合同金额、履约周期）；
输出约束：强制 JSON 固定字段，杜绝自由文字描述；
落地产品：工程投标分析、教材知识点提取、法律文档解析等创业工具。
通用调试思路（面试高频实操题）
输出效果不达预期时排查顺序：
收集 Bad Case（错误样本）；
单一变量：仅迭代提示词，增加强约束 / 少量 Few-Shot 示例，复测测试集；
若提示词优化无效，排查上层 RAG、工具调用、模型选型等工程链路。

六、提示词工程固有局限
- 无法 100% 稳定复现相同输出；
- 自由发散，缺少约束会输出无关内容。
- 无法彻底消除随机性与幻觉
- 模型概率生成本质，同一 Prompt 多次输出必有差异；医疗、金融等高严谨场景仅靠提示词无法杜绝虚假信息，必须叠加后端代码校验；
- 不存在万能通用 Prompt 模板
- 不同行业、业务逻辑、模型底层对齐差异巨大，模板必须针对性定制，直接复用效果大幅下降；
- 无法弥补模型底层能力缺陷
- 模型训练数据中无的专业知识、复杂数学难题，仅靠身份话术（顶尖专家）无法推理出正确结果；
- 企业级客服、政务系统要求输出高度统一，仅靠提示词不够，必须搭配微调、知识库、输出校验多层方案兜底。
七、高频面试易错判断题 & 核心误区
误区：写越长的提示词效果越好
纠正：冗余描述增加 token、易产生规则冲突，精炼、分层、量化才是最优；
误区：提示词可以提升大模型本身推理智能
纠正：仅约束输出，模型原生能力上限固定，微调 / 预训练才能提升底层智商；
误区单次测试效果好 = 模板稳定可靠
纠正：单次存在概率偶然性，必须大批量测试集验证，覆盖各类边界 Bad Case；
误区：提示词能让模型推导它从未学习过的专业事实
纠正：模型无底层数据支撑时，只会编造幻觉，无法可靠输出未知专业内容；
选择题标准答案：不需要改动模型参数，想要适配垂直业务场景，选用提示词工程。
八、AI 项目开发配套工程思维
数据驱动开发：所有模板优化、模型选型以批量测试数据指标为依据，不主观拍脑袋；
分层故障排查：输出异常先排查提示词→再查工具 / RAG 链路→最后更换模型；
多环节兜底：高严谨业务（医疗、政务）不能仅依赖提示词，多层校验、微调、知识库组合使用；
微服务 API 协作：企业内部 AI 能力全部接口化
九、工程项目提示词设计核心原则
拆分细分原则
大型 AI 项目不要写大一统、多功能超长提示词，必须拆分为独立小子场景专用 Prompt。
原因：提示词内容越多，模型发散、产生幻觉概率越高；拆分后精简精准，输出稳定性大幅提升。
提示词迭代思维：项目中所有 Prompt 都要持续优化迭代，持续精简、收敛约束，降低幻觉。
十、Prompt 四大核心组成模块（基础必背四要素：指令 / 上下文 / 输入 / 输出格式）
完整规范提示词由 4 部分构成，缺一不可，工程使用 Markdown 结构化排版：
1. Instruction 指令（唯一不可缺少核心要素）
定义模型需要完成的核心任务。没有指令，模型完全无法判断执行目标；输入、上下文、输出格式均可省略，指令不能省。
2.Context 上下文
任务背景：用户身份、场景、项目环境、使用人群，决定输出适配方向
参考依据：模型输出必须严格参照的材料、教材、文档、规则，禁止脱离依据自由发散。
边界约束（禁止项）：明确模型绝对不能生成的内容、拓展的领域。
历史对话、前置流程、前置推导结论也属于上下文范畴。
3. Input 输入
待处理原始素材、文本、数据、用户提问，部分无素材任务可省略输入（如直接生成学习计划）。
4. Output Format 输出格式
强制规定模型返回结构、排版、数据类型，是控制输出一致性关键手段。
十．结构化 Prompt 优势
降低模型对任务的理解偏差，减少误解；
输出高度规整统一，代码命名、报告格式、数据结构可控；
出错后可快速反向定位问题：指令模糊 / 上下文依据缺失 / 输出约束不足；
可读性、可维护性大幅提升，开源 Agent、Langchain 模板均采用该写法。
十一、约束设计核心避坑点
约束不是越多越好：过量限制会让模型畏手畏脚，本该合理发散的场景完全僵化。
约束避免互相冲突：典型冲突：前文禁止数字命名文件，后文又要求输出 0008 编号，模型逻辑矛盾输出异常。
约束区分主次
1）强约束：全程必须严格遵守（如代码驼峰命名、禁止编造数据）；
2）弱约束：仅为建议，轻微偏离可接受；
若主次混杂，模型易忽略次要规则。
禁止使用模糊中文描述（尽量量化）-中文歧义多，模糊词汇会造成模型理解偏差。
十二、模糊提示词改造示例（文章总结场景）
详细总结这篇文章
1）缺陷：
无输入载体，未提供文章文本；无量化长度约束；无目标受众、使用场景；无明确分析维度（主旨 / 风格 / 结构）；无验收标准，模型输出不可控。
2）优化思路（按照四要素补齐）
指令：对给定文章做结构化总结；
上下文：说明文章领域、总结用途、目标读者；
输入：预留文章文本传入位置；
输出：限定字数、固定分析维度、Markdown 列表格式。
3）实操技巧
向 AI 求助定制模板时，需追加指令：信息不全时分轮向我提问收集，再生成完整 Prompt，避免 AI 凭空猜测。
十三、提示词示例范式（Shot 体系，面试高频）
1 Zero-Shot 零样本
定义：仅依靠指令 + 上下文，不提供任何输入输出样例，模型纯靠文字描述理解任务。
适用：逻辑简单、规则清晰任务。
2 One-Shot 单样本
定义：提供1 组标准输入→输出对照示例，直观展示格式、风格、标签规范。
优势：无需大量文字描述格式，模型通过示例快速对齐输出习惯（代码命名、文本风格自动复刻）。
3 Few-Shot 少样本
定义：提供多组覆盖各类分类 / 边界的样本，适配有限枚举分类任务（工单分类、意图识别、标签判断）。

4核心设计要求：

工程规范：1样本具备代表性，覆盖多样的情况；2所有示例格式完全统一；
3示例并非越多越好：少量样本即可让模型习得规则，大量样例占用 token、拉高成本，收益极低。
4标签 / 分类枚举顺序必须和示例内样本顺序严格对齐（如标签 A/B/C/D，示例也按 A/B/C/D 排布）；
5复杂、边界、错误样例不能全部堆在末尾，否则模型优先记住末尾案例，忽略前置核心规则；即使模型智能提升，也无法完全消除位置偏差，生产环境必须遵循顺序对齐规范。
错误方案排除：
只放简单样例：复杂场景无法覆盖边界，模型无法区分混淆项；
无限堆砌上千条样例：token 成本暴涨、推理变慢、冗余信息干扰；
仅保留正确样例：缺少错误案例对比，模型分不清边界场景，极易误判。
正确方案：同时提供标准正确样本 + 易混淆错误 / 边界样本，帮助模型建立区分边界。
十四、标签 Label 设计规范（分类任务专用）
1标签定义：可枚举分类结果（退款 / 咨询 / 物流、情绪：开心 / 愤怒 / 平淡）；
2标签设计要求
- 边界清晰，避免语义高度近似标签（悲伤、难过二选一，不要同时存在）；
- 标签简短精炼，不冗长；
- Few-shot 样本标签不能标错，模型会完全学习错误样例；
3模型差异：GPT/Claude 等海外大模型容错更强，错样例可自动修正；国产模型容错弱，错样本直接导致输出错乱。
4拓展能力：模型可依据少量样本推理未出现标签（仅给 P0/P1 样例，可自动识别 P2 类别），属于上下文学习 ICL 能力。
十五、进阶推理范式：CoT / ToT
1 CoT（Chain of Thought 思维链）
- 原理：引导模型线性分步串行推理，拆解复杂问题为 1/2/3 有序步骤，分步输出中间推导过程再给答案；
- 适配场景：数学、逻辑、多步骤规划；
- 现状：新一代大模型（DeepSeek R1 等）内置深度思考，自动执行 CoT，无需手动写分步提示；
- 缺陷：部分模型会 “倒推”，已知答案后编造虚假推导步骤，步骤错误但答案正确；
- 优化方向：增加中间步骤校验、前置依赖判断，杜绝虚假推理。
2 ToT（Tree of Thought 思维树）
- 原理：多分支并行推理，生成多条候选思路，评估后淘汰劣质分支、择优输出；
- 适配场景：多方案选择、路线规划、多版本代码生成；
- 优缺点：推理更全面，但计算量、token 消耗远高于 CoT。
3区分考点
CoT 线性单路径；ToT 多分支树型并行，成本更高。
十六、角色（Role）提示说明
- 写法：开头定义模型身份、从业经验、擅长工具、沟通风格；
- 局限：仅改变输出语气、专业风格，无法提升模型底层推理能力；模型本身不会的知识，- 光靠身份描述依然无法解答；
- 搭配使用：角色 + 强约束 + 示例才能稳定输出专业内容。
十七、工程开发落地建议
1项目拆分：不同业务场景独立 Prompt，禁止大一统超长模板，降低幻觉；
2 结构化强制使用 Markdown 分层，方便维护、快速排错；
3 约束主次分离，规避冲突，不用模糊中文形容词，全部量化；
4 分类任务优先 Few-shot，保证样本全覆盖、格式统一、顺序对齐；
5 复杂逻辑依靠 CoT/ToT，简单任务无需额外推理增加成本；
6 不要完全依赖 AI 生成 Prompt，结合项目专属背景人工精简优化。
十八．AI 交互工程技巧
1 约束：单次提问最多 3 个问题
原因：上下文中间遗忘特性，单次抛出过多问题，模型会遗忘前面收集到的用户信息；采用多轮分步提问，每轮≤3 个。
2 实操流程（Python 学习计划提示词生成案例）
初始指令：要求 AI 通过少量提问收集全部必要信息，最终输出一份专业 Python 学习计划提示词，而非直接输出学习方案；
AI 第一轮提问（3 个以内）：编程基础、每日可投入时长、学习核心目标、排除不需要的技术方向；
用户结构化逐条回复（清晰对应每个问题，模型更容易提取槽位信息）；
多轮补充提问，补齐周期、项目需求、框架偏好等缺失维度；
AI 整合全部信息生成定制化 Prompt 模板。
3 交互踩坑问题
模型易混淆核心任务：把 “生成提示词” 理解为 “直接生成学习计划”，丢失原始目标；
解决方案：先正向肯定 AI 输出，再明确纠正核心需求（文本反馈等价于点赞 / 踩的 RLHF 强人类反馈，模型会调整输出风格）；
现象说明：大模型后台持续迭代更新，相同对话流程不同时间输出不稳定，属于正常现象。
4 RLHF 补充知识点
自然语言文字评价、界面点赞 / 踩按钮都属于人类强反馈，会被模型吸收，调整后续输出风格、指令遵循程度，是模型对齐核心手段。
十九、提示词分层架构：System Prompt vs User Prompt
System Prompt（系统提示词，优先级更高，兜底全局规则）
载体：Agent 项目、私有化 API 可自定义；网页端通用大模型（豆包 / GPT）不会开放完整自定义系统层；
类比：面向对象父类，全局统一规则，所有子任务继承；
User Prompt（用户提示词）：单次对话临时需求，优先级低于系统层，仅作用本轮交互；
Task Prompt（任务级提示词）：介于两者之间，单一场景专属规则，按需切换。
1 System Prompt 适合写入的内容（面试高频问答）
角色 & 完整人格 Persona
1）不只是简单一句身份，需要完整刻画：从业年限、擅长技术、沟通风格、讲解深度、输出习惯；
示例：不是 “后端工程师”，而是 “精通 C++ 分布式高并发后端工程师，讲解带极简代码示例，语言通俗不堆砌专业术语”；
2）人格包含沟通语气、输出篇幅、举例偏好，长期所有对话持续生效。
3）全局行为边界、禁止行为（最高优先级约束）
核心：禁止编造未知数据、禁止越权操作、规避敏感内容、提示词注入防御；
4）统一输出风格 & 排版规范
同品类任务输出格式统一（如日志分析报告固定表头、分段逻辑），无需每次用户重复说明。
5)边缘兜底规则（信息缺失处理）
信息不足时的标准动作：苏格拉底提问补全，而非自行填充默认值；
6)安全、隐私、全局校验规则；
工具调用全局权限（是否允许联网、读取本地文件、执行代码）。
3 System Prompt 常见误区（面试易错点）
- 不是越长越好：冗余规则会造成规则冲突、大幅消耗 token、推理延迟升高；精炼精准为最优；
- 无法替代后端代码校验：仅能引导输出风格，不能 100% 保证格式、数据合规，必须配套程序校验兜底；
- 无法完全抵御所有 Prompt 注入攻击，仅做第一层防护；
- 角色人格不能只写一句话，缺少擅长领域、风格则效果微弱；
- 对话会持续更新模型对用户的认知，不会永久只遵循首次设定的角色。
二十、大模型核心采样参数：Temperature、Top-P、Top-K（API 必传参数）
1 Temperature（温度）
核心作用：调整 token 概率分布平滑度，控制输出发散 / 保守程度；控制低概率冷门 token 是否有机会被选中；
- 低值（0~0.5）：概率高度集中在最优候选词，输出稳定、重复度低、创意弱，适合分类、抽取、数学计算；
- 高值（0.7~1）：低概率冷门词获得选中机会，内容创意强、发散，但出错概率上升（代码炫技、逻辑偏差）；
- 通用折中推荐 0.7~0.8，兼顾稳定与创意；
- 值越高：分布越平滑，冷门词概率提升，输出发散、创意、随机性强；
- 值越低：概率集中在最高频词，输出稳定、统一、重复度低；
特点：只改变概率权重，不限制候选词集合大小。
2 Top-P（核采样）
工作逻辑：token 按生成概率从高到低排序，累加概率直到达到设定阈值，截断后面低概率词汇；
特性：动态候选集，适配不同句子概率分布；直接缩小 / 扩大可选词池，限制候选集合。
和 Temperature 配合：温度调节概率平滑，Top-P 收缩候选池，二者对冲，需要组合调试。
作用：动态截断候选集，只累加概率从高到低的 token，直到总概率达到设定阈值，剩余低概率词直接丢弃；
Top-P=0.5：仅保留累计前 50% 概率的词汇；
Top-P=1：保留全部词汇，无截断；
。。二者关系
-效果对冲：Temperature 扩大多样性，Top-P 收缩候选范围，工程需要搭配平衡；
-共同点：仅控制生成随机性、创意度，不直接限制输出最大长度；
-实操建议：调试时先单参数调整观测效果，再组合调参，避免无法定位效果变化根源。
。。不同业务场景标准参数配置
1】低随机、高确定性场景（意图分类、实体提取、规则判断、客服分类）
Temperature 调低，Top-P 适当拉高；
需求：输出固定分类，禁止自由发散，每次结果统一。
2】高创意、发散场景（文案、方案、学习计划、课程设计）
Temperature 调高，搭配适中 Top-P，给模型充足创作空间。
3】折中通用配置（代码、问答等绝大多数通用业务）
Temperature 0.7~0.8，兼顾稳定与创意。

3 Top-K
固定保留概率最高的前 K 个 token，不看概率总和，属于静态截断；
工业使用频次低于 Top-P，二者同属采样控制参数。
4.面试考题区分
Temperature 改变概率分布形态；Top-P/Top-K 限制可选词汇集合，均不直接控制输出最大长度。
二十一、上下文窗口配套衍生问题（面试高频）
上下文窗口≠对话轮数：窗口上限是 token 总量，单轮长代码 / 文档会快速占满；
超长上下文解决方案：分层摘要、外置记忆库、分段处理、Compact 自动压缩；
Prompt 迁移问题：同一套提示词切换不同模型，输出大概率下降；
底层原因：各模型训练数据、分词器、RLHF 对齐、架构、Embedding 存在差异；
工程解法：多模型路由、分模型定制 Prompt、后端输出统一校验重试。
二十二、人格 Persona 和简单角色提示有什么区别？
答：简单角色只标注身份；完整人格包含从业背景、擅长工具、输出语气、讲解规范、全局约束，长期统一所有对话输出风格。
二十三.API 调用基础参数全解
企业项目必须通过 API 调用大模型，网页仅个人使用，API 请求核心字段：
1基础标识：model（指定模型版本）、API Key、请求 Header 鉴权；
2输入字段：用户 query、系统 Prompt、Few-shot 样例；
3采样参数：temperature、top-p；
4长度控制：max_output_tokens，限制输出最大 token，超出自动截断；
5推理开关：深度推理开关（主流模型支持，按需开启）；
6输出模式二选一：
- 一次性全量返回：适合短结果、分类识别（意图识别等），无需流式；
- 流式输出（打字机分片传输）：适合长文本对话，提升用户交互体感。
二十四。面试高频易错点
1高 Temperature≠高质量，仅代表随机性提升，容易产生无意义发散；
2低 Temperature 不代表 100% 准确，只是输出统一，仍会存在逻辑错误；
3二者无法完全约束输出格式、字段类型；高确定性业务不能只靠调参，必须叠加强 Prompt 约束 + 后端校验逻辑。
二十五、Prompt 迁移（跨模型复用提示词）
1 定义
同一套 Prompt 模板直接迁移到不同大模型（GPT、GLM、Kimi、Claude 等），输出质量、格式、指令遵循度普遍下降，是企业工程高频痛点。
2 造成差异的底层核心原因
训练数据集、模型参数量、Transformer 架构不同；
分词、Embedding 嵌入逻辑存在区别；
RLHF 人类反馈对齐程度不一致；
指令遵循、结构化输出（JSON）能力差距；
模型缓存机制：相同请求短时间命中缓存，推理不完整，结果异常。
次要影响因素（影响微弱，不显著）：服务器地域、请求时段、用户会员等级。
3 典型迁移故障案例
1】案例 1 结构化 JSON 类型不一致
需求：提取姓名、年龄，JSON 输出
①　模型 A 输出：{"name":"张三","age":31}（age 数字 int）
②　模型 B 输出：{"name":"张三","age":"31岁"}（age 字符串带单位） 后端代码解析数字直接报错，破坏业务流程。
2】案例 2 指令遵守失效
需求：仅输出【通过 / 不通过】，禁止额外解释
模型 A：通过
模型 B：通过，材料完全符合需求，满足审核标准
多余文本无法匹配枚举值，流程中断。
4 输出还是不准确
第一层：Prompt 层加固
1）增加精准强约束：明确 JSON 字段数据类型、输出字符限制、禁止冗余文字；
2）补充 Few-shot 少量样例，标准化输出范式；
3）为不同模型单独维护定制 Prompt 模板（多模型路由配套差异化提示词）。
第二层：后端校验重试层（核心兜底，不能只靠 Prompt）
1）JSON 场景：代码校验字段存在性、数据类型，类型异常自动携带错误约束二次调用模型；
2）枚举场景（通过 / 不通过）：校验输出是否属于允许值，超长 / 不匹配则重新请求；
3）统一异常重试逻辑，牺牲少量延迟换取流程稳定。
第三层：测试与上线保障
1）构建大规模 BadCase 测试集（数百条边界用例），跨模型回归测试，评估准确率；
2）模型版本迭代前执行完整回归测试，新版本指标不能大幅下跌；
3）线上降级回滚机制：某模型输出大规模降质时，路由自动切换备用模型。
5 多模型路由架构（企业标准设计）
1.路由逻辑：根据任务复杂度、业务类型分发至对应模型
- 简单分类、短问答：低成本小模型，节省 token 成本；
- 代码生成、复杂逻辑推理：代码专用微调模型；
- 多模态图文：多模态专用大模型；
2.工程收益：控制推理成本、单模型故障不宕机全业务，具备容灾备用；
3.扩展架构：多模型并行推理，汇总多份答案综合输出，提升置信度。
二十六、上下文窗口与中间遗忘（Lost in the Middle）
1 核心基础概念：Context Window 上下文窗口
- 定义：模型单次推理能够一次性处理的最大 token 总量；
- 窗口占用组成（不止用户输入）：系统 Prompt、工具描述、Few-shot 样例、全部历史对话、工具返回内容、结构化约束、长文档输入；
- 行业现状：主流模型 200K~1M 上下文窗口，窗口越大成本越高；
- 关键误区：大窗口≠模型能有效利用全部内容。
2 中间遗忘 Lost in the Middle 现象
- 定义：长上下文序列中，首尾信息模型识别、利用率极高，中间段落信息极易被忽略、理解精度大幅下降，不是完全遗忘，是识别效率低；
- 区分易混淆概念
不是早期对话全部遗忘；
不是 Prompt 漂移（角色跑偏）；
不是主题跑偏；
- 产生根源：原生 Transformer 架构序列位置特性，无法彻底根除，只能工程缓解。
3 中间遗忘工程缓解方案
- 1信息位置优化
核心任务目标、强约束、关键证据放在开头 / 结尾；
长代码、参考文档、次要推导内容放置中间位置；
- 2分层自动压缩（Compact 压缩机制，Claude 标杆方案）
触发阈值：上下文占用达到 70% 即启动压缩，不等到接近满额；
压缩保留优先级：系统规则 > 用户需求、关键业务事实 > 任务子进度；
优先舍弃：模型自身生成的大段代码、冗余输出；
压缩效果：大量冗余内容精简，释放窗口空间，降低中间遗忘概率；
- 3分层摘要 + 外置记忆：长期对话摘要存入外部检索记忆，减少窗口内冗余文本；
- 4任务拆分：超长文档 / 复杂任务拆分子步骤，分步提问，缩短单次上下文长度。
4 上下文过长的连锁负面影响
--1中间关键信息淹没，识别准确率下跌；
--2 token 消耗暴涨，推理延迟升高；
--3 预留输出 token 空间不足，回答被强制截断；
--4 模型各项综合指标全线下降。
5 Claude 上下文分层架构（行业标杆）
上下文窗口资源分层统计，清晰区分各类内容 token 占用：
-1 System 系统提示、Function 工具定义；
-2 Memory Fuse 融合历史记忆；
-3 Skills 预置工具能力；
-4 实时用户对话消息；
-5 空闲预留 token 空间；
所有记忆、任务进度以 Markdown 文档持久化存储，可人工编辑、模型自动更新读取。
二十七、工程开发通用核心思维（面试加分项）
1 API 与微服务思想
企业内部跨团队、跨服务全部依靠 API 通信，不会直接共享源码；开发必须具备读、写 API 文档能力；
2 健壮性设计
不能仅依赖模型自身能力，所有输出必须配套代码校验、异常重试、容灾降级；
3 版本与回归管理
模型升级、Prompt 改版必须做回归测试，线上出现大规模降质可快速回滚路由；
4 数据驱动优化
依靠大量测试用例、线上 BadCase 指标判断优化效果，不主观拍脑袋设计；
5 多模型容灾设计
业务不能单一依赖某一款模型，配置备选模型应对接口故障、输出降质；
6 分层解耦
提示词层、校验层、路由层、记忆层拆分，模块独立便于迭代维护。
二十八。长上下文、多轮对话与 Prompt 漂移治理
1. 基础核心概念
-1.基础术语释义
-- Multi-turn Conversation：多轮对话，用户与模型围绕同一任务（bug 修复、功能迭代、需求开发）持续交互，简单任务单轮完成，复杂问题必须多轮交互，是当前 AI 主流交互形式。
-- Context：上下文，面试 / 文档出现该词均指代上下文窗口、历史对话信息。
--Truncation：上下文截断，上下文 token 达到窗口最大值阈值时，删除 / 替换历史消息释放空间。
-2.多轮对话底层痛点
模型无法永久存储全部对话历史，上下文越长，模型各项性能指标全面下降，衍生一系列并发问题：关键信息丢失、中间遗忘、Prompt 漂移、token 成本暴涨、输出不稳定。
-3.行业通用基础处理手段：上下文压缩
--原理：对话临近窗口上限时，自动对历史对话摘要、结构化提取，仅保留关键信息，压缩后带入新一轮请求；属于有损压缩（熵定律限制，无法 100% 还原全部细节）。
--行业现状：Claude、GPT 等头部厂商有自研压缩逻辑，通用方法论可复用，各家基于底层理论做定制优化，可参考 DeepSeek、Meta 开源模型实现思路。
2. 上下文截断：优劣策略对比
（1）暴力低效策略（面试低分方案，不推荐）
--滑动窗口删除最早对话：持续丢弃最早轮次内容，大量丢失前置关键约束、任务背景。
--固定保留最近 N 轮（3/5/10 轮）：仅看轮数不区分信息重要性，早期关键业务信息直接丢弃。
--缺点：信息损耗极大，面试官问到该方案仅能拿到不足一半分数。
（2）进阶优化方案
--历史分层摘要：区分短期、长期对话，早期历史做结构化摘要替代原文，近期对话保留完整原文。
--终极方案：分层状态管理 + 外部持久记忆系统，完整留存关键事实、任务进度、用户偏好。
3. Prompt 漂移（提示词漂移）
1】定义：长对话中，即便预设系统角色、人格、输出格式、任务规则，模型仍会逐步偏离
初始约束；无对话内容关联性，所有大模型均存在，暂无 100% 根治方案。
2】和 Prompt 迁移区分：
----Prompt 漂移：长上下文多轮对话场景下模型约束偏移。
----Prompt 迁移：同一提示词下发给不同模型，输出质量存在差异，二者场景完全无关。
3】漂移工程解决方案
1）每轮稳定携带分层 State 状态层，强制留存系统基础规则。
2）周期性增强校验（每 4-5 轮执行一次）：输出后二次修正、润色，强对齐角色 / 格式约束（效果优于每轮重复携带完整 system prompt，节省 token）。
3）输出后置增强修正：模型生成结果后，单独调用一轮提示词校准人格、语言、格式，用户感知无偏移，工程落地效果最优。
4. 长上下文通用核心方法论：上下文状态分层（面试加分核心）
（1）分层设计（每轮交互持续维护，不等到压缩时再解析，降低计算开销）
所有对话 token 按重要性分级，压缩时按优先级取舍，永久高优先级内容绝不删除：
1】稳定系统规则（最高优先级）
全局固定约束：输出语言、格式、人格、安全规则，全程携带，代代遗传，绝不压缩删除。
2】当前任务状态
Agent 任务拆解后的子任务进度、待办步骤、推理链路节点；例如开发到第 2 个子任务，需记录执行断点，压缩后可无缝续跑。
3】用户状态
用户固定偏好（全程中文输出、禁用缩写等），强绑定用户身份，永久保留。
4】核心强事实数据
订单号、业务 ID、产品参数、关键需求数值等业务核心实体，丢失会导致任务完全失效。
5】短期对话历史
最近 3~5 轮完整原文，不做压缩，完整保留，保障上下文即时连贯性。
6】长期对话历史
5 轮之前全部做摘要压缩，仅留存结构化关键结论，舍弃闲聊、重复细节。
7】外部持久记忆层（检索式记忆）
独立外置存储，存放全量历史、文档、代码、知识库；模型需要时检索调取，检索不到会如实告知用户，不会编造信息。
（2）分层配套工程落地规范
1】分层状态全程维护：每一轮交互更新分层标签，触发压缩时直接读取状态，不用重复解析全文，节省算力。
2】大模型辅助分层评估：仅传入状态标签，不传入原始对话，由模型建议保留层级，搭配固定工作流并行校验，不完全依赖模型判断。
3】流转标准格式：JSON（AI 内部统一数据传输格式）
优势：跨模型兼容（GPT/GLM/Claude 互通）、易解析、支持嵌套、适合网络传输；key 必须英文，内容可多语言。
用途：承载分层状态、任务进度、用户偏好、事实数据，是工程标准存储结构。
4】人可读状态文档（Claude.md 设计范式）
- Claude 专属：自动读取同目录.md状态文档，记录项目全局状态、任务进度、检索索引，支持人工手动修改约束（如强制全程中文），每次任务结束强制更新。
- 通用落地：自建state.md状态文档，每次对话前置加载对齐进度；GPT 等闭源模型默认隐藏状态存储，不会暴露给用户。
- 不推荐使用 README 存储：README 面向外部新人项目介绍，而非 AI 状态同步载体。
5. 外部检索记忆系统原理
1】作用：替代全量扫描历史 / 项目文件，粗粒度快速定位对应文档、代码、业务模块，大幅降低 token 消耗与推理延迟。
2】运行流程
- 构建索引：对代码、业务文档、知识库生成摘要索引，记录文件 / 文件夹对应功能。
- 任务触发检索：模型识别需要历史信息，优先检索索引定位目标文件。
- 检索失败兜底：全量扫描文件，完成后更新索引，方便下次快速查询。
3】价值：解决长上下文遗忘、减少重复加载大量文档，Agent 代码开发场景必备。
6. 长上下文管理整体目标与反面问题
1】管理目标
- 保障任务连续性，不会遗忘前置约束与任务进度；
- 减少用户重复输入、重复告知偏好；
- 稳定维持模型人设、输出格式、语言规范；
- 控制 token 消耗，平衡推理速度与上下文完整性。
2】管理不当引发问题
-  Prompt 漂移、人格 / 语言风格错乱（中英文混杂、忘记输出要求）；
- 关键业务事实丢失，任务中途逻辑断裂；
- 重复携带完整 system prompt，算力、token 成本成倍上涨；
- 长对话模型指标持续下跌，输出准确率下降。
7. 面试高频考题 & 解析
考题：Prompt 漂移含义
答案：长多轮对话中，模型逐步偏离预设系统角色、格式、规则、人格约束。
考题：多轮对话工程设计注意事项
错误方案：每轮完整重复全部 system prompt，token 开销极大；最优方案分层状态管理 + 周期性增强校验。
二十八。多语言提示词工程设计
1. 多语言定义
自然多语言：中文、英文、日韩、小语种客服咨询场景；
混合语言场景：JSON 英文 key + 中文内容、多种编程语言、统一日期 / 货币格式混用。
行业背景：海外产品、跨境客服、国际化系统高频需求；国产模型中文能力最优，海外模型英文 / 小语种效果更强。
2. 多语言提示词强制明确要素
输入语言、输出语言强制指定；
专有名词、品牌、订单 ID、专业术语保留原文，附释义，禁止强制翻译；
数字、日期、货币统一规范格式；
混合语言冲突处理规则（如优先中文输出，字段名强制英文）；
混合文本优先级规则。
3. 标准多语言提示示例约束模板
plaintext
1. 自然回答使用简体中文；
2. JSON字段key必须使用英文，仅使用双引号，禁止单引号；
3. 产品、订单、API专有名词保留原始英文，不翻译；
4. 日期统一YYYY-MM-DD格式；
5. 用户输入外文时，保留原文实体，仅翻译用户诉求与情绪。
二十九。 复杂问题推理增强技术（面试核心重点：CoT、草稿本、POT、ToT、自洽采样）
前置说明
推理增强仅优化模型思考过程，无法提升模型底层原生智能，用于数学、代码、逻辑规划、多步骤业务任务，降低错误传递，平衡准确率、token 成本、推理延迟。
1. CoT 思维链 Chain of Thought
1.1 定义
引导模型分多步骤串行推导，将复杂任务拆解为有序子步骤，分步输出中间过程，再汇总最终结论，适合逻辑、数学、规划类问题。
1.2 分类
Zero-shot CoT：无示例，仅通过提示词引导分步思考（常用指令：step by step、分步骤推导）；适合缺乏样例的复杂逻辑题。
Few-shot CoT：提供完整分步推理示例，模型模仿思考路径，效果优于零样本。
1.3 标准提示规范（推荐，不只用简单 step by step）
明确拆解任务目标；
逐条列出子问题与执行顺序；
定义每一步输出约束、校验规则；
分步输出中间结果，最后汇总答案；
禁止直接跳跃输出最终结果。
2. POT 程序思维链 Programming of Thought（工程高频使用）
2.1 核心定义
让模型生成可执行代码 / 公式处理计算、逻辑运算，由程序输出精准结果，替代自然语言文字推导；程序执行结果 100% 可复现，误差仅来自需求描述，无推理随机错误。
2.2 CoT vs POT 核心区别
CoT：纯自然语言串行文字推导，存在随机推理误差；
POT：逻辑计算交给代码程序执行，结果稳定、可校验。
2.3 适用 & 不适用场景
✅ 适合：数学计算、金额优惠计算、算法刷题、数据统计、规则运算；
❌ 不适合：开放式创意、主观文案、无固定逻辑的开放任务。
2.4 POT 提示词约束模板
根据需求生成可执行计算代码；
金额数值保留两位小数；
禁止网络、文件 IO 操作；
输出代码运行中间值 + 最终结果；
增加边界异常处理逻辑。
3. ToT 树形思维 Tree of Thought
3.1 定义
放弃单条串行推理路径，并行生成多条推理分支，对每条分支单独评估、筛选，错误分支直接回溯截断，属于广度优先搜索模式。
3.2 核心特点
多候选分支并行探索，支持回溯剪枝；
需要配套分支评估标准（多维度打分筛选最优方案）；
适合多方案选择、代码生成、路线规划、多路径决策类任务。
3.3 ToT vs CoT 核心区分
CoT：单条线性推理，一条路走到尾；
ToT：多分支并行探索，劣质分支提前舍弃。
3.4. 代码生成适配逻辑
写代码存在多种实现思路，ToT 会并行生成多版代码，评估可读性、性能、边界兼容性后丢弃劣质分支，输出最优实现。
4. 自洽性采样（Self-Consistency）
4.1 原理
对同一道有唯一标准答案的问题，多次独立采样推理，汇总全部结果后采用多数投票选出最高置信答案。
4.2 适用场景
数学计算题、客观逻辑题（唯一正确解）；不适合多合理方案的规划类任务。
4.3 和 ToT 区分
ToT：单次请求内多分支并行探索；
自洽采样：多次独立完整推理，聚合全部答案投票。
4.4 局限性
多次调用模型，token 消耗、推理延迟成倍增加，简单题目无需使用。
5. 各类推理技术取舍原则
简单问题：直接输出结果，不使用 CoT/ToT/ 采样，控制成本；
数学、数值计算：优先 POT；
单路径逻辑推导：Zero/Few-shot CoT；
多方案选择、代码生成：ToT；
客观计算题、追求准确率：自洽采样；
全部增强技术均会提升 token 开销与耗时，需根据业务场景权衡。
6. 高频易错考点汇总
暴力上下文截断方案缺陷极大，面试不能作为最优解；
压缩属于有损，无法完整保留全部对话细节；
Prompt 漂移≠Prompt 迁移，场景完全独立；
JSON 仅适合机器流转，不能直接作为面向人类的项目文档；
POT 只适用于可编程、有固定逻辑的任务，不能通用所有场景；
ToT 用于多分支探索，自洽采样用于多轮独立投票，二者不可混淆；
推理增强手段仅优化思考流程，无法提升模型基础能力。
