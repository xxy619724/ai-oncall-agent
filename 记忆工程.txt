由于上下文过长核心危害
1. 成本与性能：Token消耗指数级上涨，推理延迟持续升高；超出模型上下文窗口限制。
2. 模型推理效果劣化：关键信息被无关内容淹没；长文本出现中间遗忘、多轮记忆偏移；长期错误历史反复复用，形成错误传播链；长期任务逐步偏离原始目标（目标漂移）。
3. 信息治理风险：对话摘要遗漏关键业务约束；多租户/多用户记忆、隐私泄露；检索出相似但不匹配场景的无效历史经验。
解决方案核心思路：记忆分层 + 上下文工程化治理
1. 记忆分层：
1）通用三层基础架构工作记忆、短期记忆、长期记忆
2）拓展细分记忆层（按需拆分，分层灵活不僵化）： 
情景记忆、语义记忆、程序记忆；
错误记忆：单独存储执行过程中产生的失误记录； 
情景、语义记忆可以归类到长期记忆中，不强制独立分层。
3）优先级更高的独立存储层：外部知识库、外部任务状态，单独存储业务知识与程序运行数据。
2. 上下文管理工程全套技术模块
上下文工程用来管控所有送入模型的信息，包含完整配套技术：
1）记忆检索与窗口管控：记忆筛选检索、滑动窗口、检索式记忆；
2）消息压缩处理：消息裁剪、对话摘要、上下文压缩（参考 Cloud Code 实现方案）；
3）时效管控：判定信息时效性、配置过期自动失效规则；
4）记忆写入控制：记忆门控单元（写入开关，不是单纯 0/1 开关，支持 0~1 区间百分比，5）控制信息写入权重、写入程度）；
6）记忆生命周期运维：记忆更新、记忆冲突处理、自动遗忘；
7）数据安全隔离：敏感信息治理、多用户 / 多租户记忆隔离；
8）任务约束管控：目标锚定，避免长期任务执行偏离原始目标；
9）性能优化：模型侧缓存、增量上下文更新，减少重复 Token 传输成本。

四．三大基础核心概念：Context上下文、State状态、Memory记忆
（一）Context 上下文

1. 定义：单次大模型推理时，提供给模型的全部信息，是模型本轮推理可见的所有内容，不等于单轮用户输入 input。
2. 完整组成
- 系统级 System Prompt（系统通用规则，角色定义、全局约束）、开发级 Develop Prompt（用户级）
- 当前轮用户输入；
- 短期完整对话历史、长期压缩对话摘要；
- 任务全局目标、实时任务状态（任务状态信息）；
-工具列表 ，工具定义描述、历史工具调用返回结果、项目/业务检索文档（检索信息）、外部知识库/数据源信息；
- 输出格式约束。
3. 存储与传输优化
- 推荐JSON结构化封装，解析效率高于Markdown；
- 模型端支持缓存与增量更新：不变内容（系统提示词、全局目标）仅首次传入，后续仅推送变化部分，减少Token重复编码开销。
4.系统和开发级区别
系统Prompt（System Prompt）
存储内容
全局固定基础设定，每次LLM请求开头传入，极少改动
1. Agent基础角色定位
例：你是一名C++后端开发助手
2. 基础通用行为准则
例：回答先给出方案，再展开思路
3. 全局输出格式规范
例：代码添加注释、优先中文作答、结果分点输出
4. 底层安全护栏、硬性禁止项
例：不编造不存在接口、不输出非法内容
关键特点
1. 一次性配置；不会自动吸收对话中新出现偏好/规则
2. Token不宜过大，只放通用不变规则；个性化长期规则放长期记忆库
3. 位置：请求报文最前置
开发Prompt（开发者拼接/工程侧Prompt，不是LLM官方字段名）
说明：开发Prompt = 工程代码动态组装的全部附加提示素材，运行时由程序拼装，每一轮请求都会变化。 
存放内容（程序动态拼接进去） 
1. 从长期记忆检索召回出来的摘要、用户长期偏好、项目长期约束、历史踩坑经验
2. 短期记忆：最近若干轮对话历史、会话临时要求、会话内中间结论
3. 工作记忆：当前子计划、最近工具调用返回结果、待确认事项
4. State任务状态片段：当前执行节点、已完成步骤、重试次数等关键状态
5. RAG检索出来业务文档片段
6. 当前轮用户最新输入
7. 输出格式二次临时约束（本次任务专属，不是全局规则） 
特点
1. 每轮请求不一样；根据任务进度、记忆检索结果动态生成
2. 来源：数据库、向量库、会话缓存、工具返回、状态机
3. 拼接到系统Prompt之后

重点补充：System Prompt、Develop Prompt 分别写入哪些内容
1. System Prompt（系统级提示词，全局固定、极少修改，模型长期缓存）
Agent 角色、身份、专业定位；
全局固定职责、行为准则、基础行事逻辑；
通用输出基础规范（基础行文语言、基础格式、禁止行为）；
全局安全约束、隐私处理规则、通用边界限制；
基础推理底层逻辑、通用思考框架；
不随单次会话、单次任务变更的永久通用规则。
例：你是后端开发 Agent，严谨规范，禁止编造不存在接口，输出分步骤结构化，不泄露用户隐私。
2. Develop Prompt（开发 / 项目级提示词，绑定项目，项目内长期生效）
当前项目专属全局目标、项目背景、项目技术栈约束；
项目专属输出标准、文档规范、代码规范；
项目固定业务规则、领域专属术语定义；
项目固定工具使用规则、接口调用规范；
项目级长期偏好（如所有报告末尾附带引用、默认中文输出）； 仅切换项目时修改，同一项目下所有会话通用。

（二）State 任务状态
1. 定义：Agent 工作流执行过程中，程序实时生成的运行数据，具备权威、真实属性，是模型决策最高优先级参考
两种存储设计方案二选一：
独立于上下文，单独抽离 JSON 字段；
内嵌到上下文作为补充信息，两种设计均合理。
2. 存储核心内容
- 原始任务目标、当前执行节点、已完成步骤、工具重试次数；
- Checkpoint快照编号（用于任务中断恢复）；
- 工具调用ID、审批/校验状态；
- 缓存引用、大文件 / 数据库存储路径地址；
-中间执行结果、临时快照数据。
3. 部署设计：可独立于上下文单独存放，也可嵌入上下文；无需每轮全量传入，支持增量推送。
（三）Memory 记忆工程
1. 定义：持久化存储经过筛选、结构化、可跨会话反复检索复用的全部历史信息，不只是对话摘要，必须配套专业数据组件，拥有独立完整生命周期。
2. 完整生命周期：写入 → 结构化存储 → 检索召回  → 提取送入上下文推理（使用） → 信息更新 → 冲突处理 → 时效遗忘/删除。
3. 配套底层存储组件（各司其职）
Memory 配套存储组件及作用
1）轻量本地存储：SQLite、JSON 文件、Markdown 文档，轻量化存储小型记忆片段；
2）键值存储 Redis：存放会话临时状态、高频短期缓存；
3）向量数据库（FAISS/Milvus 等）：服务检索环节，文本向量化后通过余弦相似度计算向量夹角，判断语义相似度，快速召回相似历史内容，RAG 与 Agent 记忆核心组件；
4）Elasticsearch ES：海量非结构化全文文档高速检索；
5）图数据库（知识图谱存储）：存储实体、节点、关系链路，支持逻辑推理； 举例：企业股权、子公司层级、技术学习路线等强关联实体数据；
6）传统关系型数据库 MySQL/Oracle：仅作为外部业务数据源（订单、余额等业务数据），不直接作为 Agent 记忆载体；
7）专用记忆服务：企业级一站式记忆读写、检索、遗忘管控平台，各家实现方案不统一。
4. 关键设计要求：单纯数据库存储不等于记忆工程；完整记忆系统必须具备：更新机制、冲突消解、精细化遗忘机制、高精度语义检索。
 
一、工作记忆
1. 属性：最临时、时效性最新的记忆，容量极小；与上下文高度重叠，可内嵌至 State；
2. 存储形式：无需高性能存储，仅用简短形式存储数据。
3. 特征：仅针对单一轮对话交互，每一轮对话都会更新变化。无持久化需求。
4. 存储内容：当前任务目标，当前子任务、当前计划步骤、最近一次工具观察结果、临时计算结果、待确认问题； 
二、短期记忆STM
1. 服务对象：完整的当前单次会话（单一会话包含多轮对话）
2. 存储内容
- 最近若干轮对话（如5-6轮）完整原文，无需摘要，可全量放入上下文窗口；
- 最近多次工具观察结果；- 会话内临时用户约束- 对话内短期产出的中间结论。
3. 特点：不做摘要压缩，完整送入上下文；会话结束后内容归档，提炼摘要存入长期记忆。 
三、长期记忆LTM
1. 服务对象：跨会话、长周期大型项目持久存储，支持隔天、隔窗口接续任务；
- 适用场景：大型长期项目，会话会反复关闭、重新打开，无法依靠单一会话窗口承载全部信息。
2. 存储内容
1）稳定长效信息（基本不易失效，仅换项目/极长时间后失效）
- 用户固定偏好、用户基础信息；项目全局目标、项目背景资料、长期输出约束
- 压缩后的历史对话摘要、历史任务经验、过往错误修复总结；
2）时效型任务信息（会随时间自动失效）
- 长期任务进度、过往历史任务记录（如数年前完成的工作）；
- 举例：2天前进度当下有用，隔数天后无使用价值，自动失效。
4. 基础特性
·  强制持久化存储，多租户权限隔离、版本控制；
·  精细化遗忘机制：时效性进度信息会过期，经验、规则类信息长期留存；
·  不存储全量原始对话，仅保留摘要；
·  依赖向量库、图数据库完成检索，按需提取片段注入上下文
5. 调取能力：所有存入的长期任务状态信息，均可从Memory中检索调取。
四、三者核心区分总结
1. 工作记忆：单轮对话，临时、容量小，存本轮单次工具结果；
2. 短期记忆：单完整会话，近多轮完整对话+多轮工具结果+短期约束结论；
3. 长期记忆：跨多会话，存储长期项目、用户偏好、历史经验、历史任务进度，支持持久化、遗忘、权限管控。
五、配套辅助概念区分（易混淆）
1. Checkpoint检查点：某一执行时刻完整快照，用于任务中断后恢复状态；
2. Knowledge Base知识库：外部固定领域/企业业务知识集合，独立于Agent自身记忆；
3. Cache缓存：短期可复用的工具、计算结果，用于减少重复执行开销；
4. 优先级规则：模型推理决策优先参考权威State状态，其次是上下文筛选信息，最后检索Memory历史记忆。
  
场景
用户长期规则：所有报告优先中文输出，文末附带完整引用信息（项目级长期偏好）
存储位置：存入长期记忆；新建会话时自动检索，注入 System Prompt 送入上下文；
冲突场景：本次会话用户临时要求 “本次文档英文输出，不需要引用”；
处理逻辑： 
1）当前会话明确指令优先级高于长期记忆；
2）临时约束仅保存在短期记忆，会话关闭直接销毁，不写入长期记忆；
3）若用户明确永久修改规则，才更新覆盖长期记忆原有约束。
六、核心工程设计原则
1. 上下文不是全量数据，是筛选后的关键信息集合；
2. State状态具备最高权威性，业务动态事实必须以外部业务库为准，不能复制到记忆作为唯一依据；
3. Memory记忆工程核心不止存储，检索、更新、冲突处理、遗忘缺一不可，检索要求精准精简；
4. 指令冲突规则：当前会话临时指令优先级 > 长期记忆全局约束；临时会话指令不写入长期记忆，只有永久变更类需求才更新长期记忆；
5. 禁止让模型直接修改关键State，业务状态更新必须通过程序校验、确定性逻辑执行。
七、行业常见认知误区
1. 误区1：聊天历史=全部Agent记忆 → 纠正：聊天历史仅短期记忆来源，长期记忆只存压缩摘要；
2. 误区2：模型能自动读取数据库全部记忆 → 纠正：模型无外部存储访问能力，所有历史必须人工检索后送入上下文；
3. 误区3：长期记忆必须用向量数据库实现 → 纠正：向量库仅用于语义检索，长期记忆是多组件协同架构，不是单一组件；
4. 误区4：业务订单、余额等数据可复制为Agent权威记忆 → 纠正：动态业务数据以外部业务系统为准，记忆仅存储索引，不拷贝实时业务数据；
5. 误区5：允许模型直接修改核心任务State → 纠正：关键状态变更需程序校验，不可完全信任模型输出。
6误区：新旧指令冲突时沿用长期记忆偏好 纠正：当前会话明确指令优先级更高；临时修改不持久化，永久变更才更新长期记忆。
·  误区：System、Develop Prompt 混写不分 纠正：通用底层规则放 System，项目专属约束放 Develop，临时单次需求不放二者；
·  误区：新旧指令冲突优先沿用长期记忆 / Develop 规则 纠正：当前会话明确临时指令优先级更高，仅永久变更才更新长期记忆与 Develop Prompt。

长期记忆不是单一数据库实现，是多组件协同的持久化记忆系统，分为「持久存储载体」「检索加速组件」「结构化关系存储」「缓存辅助组件」四大类，所有组件配合完成长期记忆的写入、存储、检索、更新、遗忘全生命周期。
一、持久化基础存储组件（永久落地存原始记忆数据）
负责把摘要、用户偏好、项目规则、历史经验落地持久化，断电 / 关会话不丢失。
SQLite 本地轻量数据库 
用途：单机小型 Agent、本地私有化部署，存储结构化长期约束（用户固定偏好、项目输出规范、历史错误经验清单）；
存储内容：结构化键值记忆、项目长期配置、精简对话摘要；
优势：无需单独部署服务，轻量化，适合个人 / 单机场景。
JSON / Markdown 文件存储 
用途：轻量配置型长期记忆，纯文本规则类信息；
存储内容：Develop 级项目约束、固定输出模板、用户长期偏好；
局限：海量历史对话不适合，检索效率极低，仅存静态规则。
MongoDB 文档数据库 
用途：企业级多租户 Agent 主存储；
存储内容：结构化记忆对象、跨会话对话摘要、长期任务进度、用户完整记忆档案；
优势：原生支持 JSON 结构化、易扩展、支持多租户隔离、方便记忆版本管理。
MySQL/PostgreSQL 关系数据库（辅助） 
不直接存对话记忆，只存记忆元数据：记忆归属租户 ID、创建时间、过期时效标签、权限、索引关联 ID；
动态业务数据（订单、余额）单独业务库，不存入长期记忆本体。
二、语义检索核心组件（长期记忆召回必备）
长期记忆数据量大，不能全量送入上下文，依靠以下组件做相似度召回，只取相关片段。
向量数据库（Milvus、FAISS、Chroma、Weaviate） 
核心定位：长期记忆最核心检索组件；
工作逻辑：将对话摘要、历史经验、项目文档向量化，通过余弦相似度计算语义相近内容；
长期记忆用途：跨会话召回相似历史任务、相似报错经验、匹配项目历史方案；
搭配逻辑：原始记忆存在 Mongo/SQLite，向量库只存向量 + 记忆 ID，检索后回查数据库拿原文。
Elasticsearch（ES）全文检索引擎 
定位：关键词 + 文本模糊检索补充向量库；
长期记忆用途：按关键词、时间、项目标签过滤长期记忆，筛选指定时间段、指定项目的历史摘要；
适用：需要精确匹配业务关键词、过滤时效记忆场景。
三、关系推理存储组件（知识类长期记忆专用）
存储实体关联、逻辑链路类长期知识，属于长期记忆拓展层。 图数据库（Neo4j）
存储内容：长期项目实体关系、业务知识图谱、技术依赖关系、历史任务关联链路；
长期记忆场景：大型开发项目、法律咨询、企业架构类 Agent；
作用：支持多跳逻辑推理，弥补向量库仅语义匹配、无关系推理的短板。
四、高速辅助缓存组件（提升长期记忆读取速度）
Redis 键值缓存
不属于持久主存储，是长期记忆的高速缓冲层；
用途：缓存高频访问的长期记忆（当前项目固定规则、高频用户偏好）；
机制：从向量库 / MongoDB 检索到长期记忆后，存入 Redis 短时缓存，重复会话无需重复检索；
同时存储记忆门控开关、记忆过期时效标记。
五、专用上层记忆服务（企业整合层）
不属于底层数据库，是封装所有存储组件的一体化服务：
统一封装写入、向量化、检索、冲突更新、遗忘清理逻辑；
统一处理多租户隔离、权限校验、记忆版本；
内部自动调度向量库、ES、Mongo、Redis，业务侧无需操作多类中间件。
六、长期记忆完整组件协同流程
会话结束 → 短期对话摘要处理；
记忆门控判断是否写入长期记忆；
结构化摘要存入 Mongo/SQLite 持久存储；
文本向量化存入向量数据库，绑定记忆唯一 ID；
记忆元数据（时效、租户、标签）存入 MySQL；
高频记忆同步写入 Redis 缓存；
检索时：向量库语义召回 → ES 关键词过滤 → Redis 缓存命中加速 → 拉取完整记忆送入上下文；
遗忘机制定时扫描：清理过期时效记忆，同步删除向量库、缓存、主库对应数据。
七、分层区分：哪些组件不是长期记忆组件
纯 Redis 临时会话数据 → 属于短期记忆 / 工作记忆缓存，不是长期持久载体；
仅存当前会话原始对话的 JSON 文件 → 短期记忆；
业务 MySQL 原始订单库 → 外部数据源，不属于记忆体系；
滑动窗口内存列表 → 短期内存，无持久化，不属于长期记忆。
八、最简 / 标准 / 企业三套组件搭配方案
单机轻量化 Agent（最小长期记忆组件） SQLite + Chroma 轻量向量库 + Redis
通用标准 Agent（主流方案） MongoDB（主存储） + Milvus 向量库 + ES + Redis
大型复杂项目 Agent（带知识推理） MongoDB + Milvus + ES + Neo4j 图数据库 + Redis + 专用记忆服务 + MySQL（元数据）
 
一、三类基础记忆类型
1. 语义记忆
存储事实、概念、实体关系、属性信息；不区分信息来自哪一次具体事件。
示例：客户惯用语言、所属行业、报告末尾必须附带审计编号等长期事实要求。
工程处理方式：可直接放入提示词，不一定单独分层。
2. 情景记忆
保存过往具体任务、事件、执行轨迹；记录时间、动作、执行结果，可复现当时场景，属于强经验型记忆。
示例：上次退款查询接口超时；上周三某任务客户拒绝特定报告格式；某函数修复方案在场景中执行失败及后续修改过程。
3. 程序性记忆
完成任务所需的规则、步骤、策略、操作技能，强流程导向。
示例：客服工单审查SOP、合同审查SOP、工具选择SOP、退款/物流查询标准流程。
工程处理方式：建议单独抽象一层做精准记忆；也可并入其他记忆层。
补充：三类记忆分层只是工程方案，不强制拆分，可根据场景合并实现。 
二、上下文窗口基础概念
1. 定义：模型单次能够处理的输入+输出token总量上限；约束来自模型本身能力、API限制。
2. Token占用构成
- 高占用项：系统提示词、工具定义、对话消息、检索得到的外部资料
- 必须预留：输出token空间、安全空闲阈值，不可把窗口完全打满。
三、窗口维护常用手段（一般组合使用，不单独只用一种）
1. 滑动窗口 
机制：队列逻辑，按时间先后，仅保留最近N轮消息/最近一段token内容；更早进入的消息优先移出上下文。
特点：单纯以时间顺序淘汰历史，不会评估消息重要程度。 
2 消息裁剪
机制：依据token预算、消息类型、消息重要性评分，执行删除/截断消息。
关键要点：禁止机械按时间删除；需要保护系统规则、当前任务目标、关键约束、必要证据、未完成任务，不能随时间被清理。
区别滑动窗口：滑动窗口＝优先时间淘汰；消息裁剪＝兼顾重要性做取舍。
3. 摘要压缩（上下文压缩）
基础流程：旧摘要 + 新增消息合并 → 重新提取摘要 → 使用新摘要替换完整旧历史。
进阶方案：分层摘要，分开处理对话摘要、任务级摘要、全局偏好/规则摘要；多个低层摘要再合并为高层全局摘要，不把所有消息混在一起压缩。 
四、上下文维护常见错误做法&认知误区 
❌错误操作
1.永久完整保存全部历史，不做任何压缩裁剪
2.只保留最新消息，丢失原始任务目标、关键约束
3.只用单段普通自然语言概括全部历史状态，极易丢失信息
4.删除原始证据，后续无法审计复盘
5.工具调用请求与对应的工具返回结果拆开裁剪，二者失去映射关系
6.将系统安全规则交给摘要模型压缩改写（安全规则必须完整保留）
❌认知误区
1.上下文窗口越大＝不需要记忆管理：窗口再大依旧存在上限，长期对话依然要管控
2.仅按消息条数裁剪，不统计token消耗
3.把system提示词交给摘要压缩
4.摘要压缩做到无损、100%忠实原文：压缩天然有损
5.只留存最近对话，不锚定原始目标
6.忽略输出token预留预算
7.工具返回结果越完整越好：工具返回token量大，成本不可控；最优方案：按需注入关键片段、保留可追溯引用，而非全量塞入上下文

压缩/裁剪/摘要要把控力度：动作太轻无法释放token；力度过大丢失关键信息；摘要、裁剪策略依赖高质量提示词调校，平衡二者。
 
五、上下文分区设计（推荐架构）
1. 不可压缩区：系统规则、安全规则、本轮用户明确指令；禁止摘要、裁剪
2. 可压缩区：老旧历史对话、已经生成过的历史摘要，可以参与重新摘要压缩
3. 目标锚定区：原始任务目标、成功标准、关键约束、当前执行计划步骤；需要强保留
4. 近期交互区：最新对话消息、最新工具返回观测结果
5. 可检索区：长期记忆库内容、外部知识库资料；按需检索注入上下文
6. 输出区：专门预留的输出token预算
Token分配思路：规划各分区配额：系统&安全规则、工具定义、目标约束、近期消息、长期检索记忆、外部文档、输出预留、安全余量。
 
六、摘要工程要点
1.摘要形式：优先结构化摘要，不使用单段自由文本做全部历史总结。
2.组合压缩策略示例
- 保留最近K轮原始消息；
- 原始目标、关键约束强制保留，不参与摘要；
- 工具返回结果做证据化压缩：记录请求来源、核心结论、关键证据片段，提炼对下一步推理有用信息，丢弃冗余原始数据。
3.摘要校验必要性
摘要生成后必须校验/人工教研，也可以使用独立评估大模型校验；检查项：目标含义有没有被改写曲解、关键约束完整度、未确定信息有没有被写成事实、待办事项有没有丢失、工具报错不要误固化为业务结论。
4.摘要质量难点：缺少简单可靠量化指标；优化手段：单一变量实验，只修改摘要方案，观察下游任务成功率、步骤拆解合理性；摘要质量差会造成模型遗忘关键节点、重复执行已完成工作，浪费token。
七、核心结论：对话即将超限，最优方案
正确方案：固定保留目标和关键约束；旧消息生成结构化摘要；保留近期消息；按需检索长期历史。
错误方案辨析
1.永久删除早期消息，不留摘要：丢失历史经验
2.直接暴力截断至模型硬上限，不考虑语义完整：破坏语义
3.直接更换更大窗口模型，完全不做上下文管理：大窗口仍存在上限，长期会话依然溢出
八、检索式记忆
1.概念
不把全部历史一次性放进上下文；根据当前任务需求，从独立记忆库检索相关历史片段，筛选后注入本轮上下文；多用于Agent。
2.完整标准流程
1.构建记忆查询 → 2.权限过滤 → 3.候选召回 → 4.重排序(Rerank) → 5.去重、冲突处理 →  多样性取舍（单一最优 / 多条差异化结果）→6.依据token预算裁剪候选片段 →7.注入上下文
步骤顺序：
1. 获取当前任务、用户输入，提取查询要素
2. 权限、作用域硬过滤
3. 关键词+向量检索产出候选记忆集合
4. 多因子加权综合打分，执行Rerank重排
5. 去重、冲突消解
6. 多样性取舍（单一最优 / 多条差异化结果）
7. 在Token预算约束下精细化剪裁（禁止粗暴截断）
8. 将加工后的记忆片段注入上下文

3.三类检索手段
1.向量检索：依靠语义相似度匹配，数学可解释
2.关键词检索：匹配关键词出现频次
3.混合检索：向量语义+关键词共同检索，加权打分合并结果
重排序(Rerank)：对召回候选集做精细相关性打分、重新排序，筛出高价值记忆。
4.综合评分与时间衰减（原版不变）
1）. 综合得分多因子加权，配置独立权重系数；维度：关键词匹配、向量相似度、业务相关性、重要性；叠加时间衰减因子。
2）. 时间衰减规则
- 时间越近初始分数越高；随时长增加衰减因子拉低总分
- 超过时效阈值，得分低于下限，不再召回（软遗忘）
- 时间只是打分因子之一，不可单独作为筛选条件

九、检索式记忆 VS RAG（核心区分）
共同点：召回、重排、权限过滤流程相似
1.检索对象不同
- 检索式记忆(Agent记忆)：Agent历史动作、执行结果、过往失败经验、用户长期偏好；多为结构化记录(JSON等)- 记忆检索：Agent运行过程自动沉淀历史：历史任务进度、用户长期偏好、历史方案、踩坑经验；数据随会话动态生成。
- RAG：企业知识库、文档、手册、行业资料等静态外部知识；多为长篇自然语言文档、代码库，独立于Agent历史；文档一般人工录入维护。
2.向量构建方式不同
记忆库多处理结构化片段；RAG需要适配长文档、代码等特殊数据做向量化，二者方案不一样
3.生命周期机制不同
- Agent记忆：具备写入门控、遗忘机制、新旧记忆冲突更新逻辑
- RAG知识库：更新少、几乎没有自动遗忘机制，侧重版本管理
4.召回&重排目标差异
- Agent记忆检索：追求精而简，少量关键记忆辅助当前任务
- RAG检索：优先保证准确，避免返回错误类目资料，可以返回较多候选材料
补充：仅向量召回存在歧义缺陷（一词多义），工程实践普遍采用混合检索提升可靠性。
5数据源不同
‑RAG：获取客观领域知识，辅助回答问题；单次问答居多。
‑记忆检索：恢复任务上下文、保持长期行为一致性，多用于跨会话接续长任务。
6过滤约束不同
‑普通RAG大多做文档权限过滤即可。
‑Agent记忆检索强制：租户、用户、任务作用域、指令生效范围（临时/长期）多层过滤；还要做冲突消解、区分版本。
十、为什么固定Top‑K有缺陷 & 不设固定Top‑K思路
1. 固定Top‑K痛点
不同用户Query、不同业务场景，需要的记忆条数差异很大：有的问题只需要1条记忆，复杂任务需要4‑5条；写死K值无法适配全部case。
只调一个固定K（例如K=3/5），靠人工拍数值说服力弱；即便做测试选出最优K，也只是整体平均最优，单一场景未必合适。
2. 工程替代思路（不依赖固定Top‑K）
1）分数阈值截断：重排之后，只保留综合得分≥设定阈值的全部条目，条数动态变化，而非强制取前N条；
2）两层控制：先用得分阈值粗筛候选，再在总Token配额下做裁剪；
3）阈值可分场景配置：简单问答阈值高，长周期复杂任务阈值适当放宽；
说明：Top‑K是简单暴力方案；工业级记忆检索优先「分数阈值 + Token预算双重约束」代替硬编码Top‑K。
五、典型场景
新开对话窗口，用户要求按昨天方案继续工作：召回历史时间范围内任务计划、步骤、状态；召回项目长期偏好；摘要加工注入新会话上下文。
六、去重冲突两个案例
案例1 输出约束冲突
召回三条：①用户偏好中文；②上次任务临时英文；③系统默认中文。
处理：区分临时指令/长期约束；任务专属临时约束降权，保留长期有效规则。
案例2 语义相似但业务不兼容
处理中国退款，向量召回欧洲退款流程。
解决：检索前置业务标签过滤（地区、业务线），提前剔除无效案例。
七、选择题结论
✅正确：先权限硬过滤；综合语义、关键词、时间、重要性、置信度加权再重排。
❌错误：只靠相似度、全量灌入Prompt、仅返回最新记忆。
八、认知误区清单（更新第3条Top‑K表述）
1. ❌向量相似度高 = 记忆正确
2. ❌权限作为打分项；权限必须前置硬过滤
3. ❌Top‑K越大越好 / 强行固定单一Top‑K
固定K只能做到全局平均最优，无法适配所有场景；优先采用得分阈值过滤+Token上限约束动态控制返回条数。取值测试仅用来评估基线效果，不是最终生产方案。
4. ❌仅拿最后一句消息构造检索查询
5. ❌忽略记忆时间、版本
6. ❌跳过去重、冲突处理
7. ❌历史记忆优先级高于本轮用户最新指令（优先级：当前指令 > 历史记忆）
8. ❌记忆库替代实时业务库；高频变动字段存入记忆使用占位符，召回后调用业务接口刷新真实值
